- [[../backlog|backlog.md]] ลิสต์สเปคครบทั้ง 3 ฉบับที่มีอยู่จริงใน `01-spec/` ไม่มีลิงก์ตาย

- ไม่พบความขัดแย้งระหว่างสเปค — สเปค dashboard และ audit log ต่างอ้างอิงกลับไปยังสเปค QR ordering อย่างสอดคล้องกัน (เช่น กติกา "นับเฉพาะออเดอร์ที่ชำระเงินสำเร็จ" ถูกใช้ตรงกันทั้ง 2 ฉบับ) และสิทธิ์การเข้าถึง audit log (`owner`/`system_admin`) ถูกระบุชัดว่าเป็นคนละชุดสิทธิ์กับ dashboard ยอดขาย (`sales_viewer`) ไม่ทับซ้อนกัน
- โปรเจกต์ยังอยู่ในช่วงต้น (3 สเปค, ทุกฉบับสถานะ "ร่าง") จึงยังไม่มี Feature List หรือ User Journey มาก่อน — เอกสารนี้เป็นฉบับแรก ไม่ใช่การอัปเดตของเดิม

## แนวทางการแตก Feature List (3 แนวทางที่พิจารณา)

| # | แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|---|
| 1 | **1 feature = 1 scope bullet ("ทำ") ของแต่ละสเปค** — แตกละเอียดที่สุด | Traceability สมบูรณ์แบบ 1:1 กับสเปค, ตรวจสอบความครบถ้วนกับสเปคง่าย, จัด MoSCoW ได้ละเอียดต่อรายการย่อย | ลิสต์ยาว (14+ รายการ) และกระจัดกระจาย, บาง bullet เล็กเกินกว่าจะเรียกว่า "feature" ที่สื่อสารกับผู้บริหาร/ลูกค้าได้ |
| 2 | **1 feature = 1 ความสามารถหลัก/epic ต่อสเปค** (group ตาม user story) | อ่านง่าย เหมาะสื่อสารกับ stakeholder ที่ไม่ใช่สายเทคนิค, สอดคล้องกับ user journey ตามธรรมชาติ (1 feature ≈ 1 ช่วงของ flow) | เสี่ยงสูญเสีย traceability กลับไปยัง scope bullet ต้นทาง ถ้าไม่บังคับอ้างอิงในคำอธิบาย |
| 3 | **Hierarchical: 1 สเปค = 1 epic แตกเป็น sub-feature หลายชั้น** | รักษาทั้ง granularity และ traceability ได้ดีที่สุดในทางทฤษฎี | โครงสร้างซับซ้อนเกินจำเป็นสำหรับโปรเจกต์ที่มีแค่ 3 สเปค, เพิ่ม overhead การดูแลรักษาเอกสารโดยไม่ได้ประโยชน์เพิ่มมากนักในขนาดปัจจุบัน |

**แนวทางที่แนะนำ: แนวทางที่ 2 (group ตาม epic) โดยบังคับให้ทุก feature มี reference กลับไปยัง scope bullet/business rule ต้นทางเสมอ** — ได้ความอ่านง่ายของแนวทาง 2 ไว้ใช้สื่อสารกับเจ้าของร้าน (ผู้ใช้ปลายทางของเอกสารชุดนี้ ซึ่งไม่ใช่สาย technical) บวกกับ traceability ของแนวทาง 1 ผ่านคอลัมน์อ้างอิงในตาราง โดยไม่ต้องแบกโครงสร้างหลายชั้นของแนวทาง 3 ซึ่งเกินความจำเป็นเมื่อมีสเปคเพียง 3 ฉบับ ถ้าจำนวนสเปคเพิ่มขึ้นมากในอนาคตจนกลุ่ม epic เดียวมี feature เกิน ~8-10 รายการ ควรพิจารณาย้ายไปแนวทางที่ 3

## รายละเอียด Feature

### Epic: ระบบสั่งกาแฟผ่าน QR Code

#### QR-01 — สั่งเมนูผ่าน QR Code ประจำโต๊ะ
**คำอธิบาย**: ลูกค้าสแกน QR Code ที่ติดประจำโต๊ะ เปิดเป็นหน้าเว็บสั่งเมนูทันทีโดยไม่ต้องติดตั้งแอป ระบบระบุหมายเลขโต๊ะอัตโนมัติจาก QR ที่สแกน
**เหตุผลของ MoSCoW (Must)**: เป็น entry point เดียวของทั้งระบบสั่งซื้อ — ไม่มี fallback อื่น (ไม่ทำแอปมือถือ, ไม่ทำช่องทางสั่งแบบเดิมผ่านแคชเชียร์ในเอกสารนี้) ถ้าไม่มี feature นี้ ฟีเจอร์อื่นทั้งหมดในระบบสั่งซื้อใช้งานไม่ได้เลย
**Business rule ที่เกี่ยวข้อง**: "1 QR Code ผูกกับ 1 หมายเลขโต๊ะ ระบบต้องรู้ว่าออเดอร์มาจากโต๊ะไหน"
**ประเด็นเปิด**: ไม่มี

#### QR-02 — ตะกร้าสินค้า + ชำระเงินออนไลน์
**คำอธิบาย**: ลูกค้าเพิ่มเมนูลงตะกร้าและชำระเงินผ่านระบบได้ทันที โดยไม่ต้องเดินไปจ่ายที่แคชเชียร์
**เหตุผลของ MoSCoW (Must)**: เป็นเงื่อนไข gate ของทั้งระบบ — ออเดอร์จะถูกส่งไป KDS และคำนวณแต้มสะสมได้ก็ต่อเมื่อชำระเงินสำเร็จเท่านั้น (business rule) ถ้าไม่มี online payment จะขัดกับ scope ที่ยืนยันแล้วว่า "ไม่ต้องเดินไปแคชเชียร์"
**Business rule ที่เกี่ยวข้อง**: "ออเดอร์จะถูกส่งไปแสดงบน KDS ก็ต่อเมื่อการชำระเงินสำเร็จแล้วเท่านั้น"
**ประเด็นเปิด**: ช่องทางชำระเงินที่รองรับ (พร้อมเพย์/บัตรเครดิต/วอลเล็ต) และการจัดการกรณีชำระเงินไม่สำเร็จ/ยกเลิกออเดอร์ ยังไม่ระบุ — รอตัดสินใจรอบถัดไปตามที่ระบุในสเปคต้นทาง

#### QR-03 — ระบบสมาชิก/สะสมแต้ม
**คำอธิบาย**: ลูกค้าที่เป็นสมาชิกได้แต้มสะสมอัตโนมัติจากยอดชำระที่สำเร็จ
**เหตุผลของ MoSCoW (Should)**: flow หลัก (สั่ง → จ่าย → ขึ้น KDS) ส่งมอบคุณค่าหลักของระบบได้แม้ยังไม่มีระบบแต้มสมบูรณ์ และตัวสเปคเองระบุว่าอัตราการสะสม/แลกแต้มยัง "ไม่กำหนด" จึงเป็นความสามารถที่ต่อยอดเพิ่มความคุ้มค่าได้ ไม่ใช่ blocker ของ core transactional flow — จัดเป็น Should ไม่ใช่ Must เพียงเพราะ core flow เดินได้โดยไม่ต้องรอ feature นี้เสร็จสมบูรณ์ก่อน (ไม่ได้แปลว่าตัดออกจากรอบนี้ ยังอยู่ใน scope ที่ยืนยันแล้ว)
**Business rule ที่เกี่ยวข้อง**: "แต้มสะสมคำนวณจากยอดชำระที่สำเร็จเท่านั้น"
**ประเด็นเปิด**: อัตราการสะสม/แลกแต้มสมาชิกยังไม่กำหนด — ต้องระบุก่อนเริ่มพัฒนาจริง

#### QR-04 — จอแสดงผลออเดอร์ (KDS) แบบเรียลไทม์
**คำอธิบาย**: ออเดอร์ที่ชำระเงินสำเร็จแสดงผลบนจอในร้านให้บาริสต้าเห็นแบบเรียลไทม์
**เหตุผลของ MoSCoW (Must)**: ถ้าไม่มี feature นี้ ออเดอร์ที่ลูกค้าจ่ายเงินแล้วจะไม่มีใครรู้ว่าต้องทำเครื่องดื่ม — operational flow ขาดตอนสมบูรณ์ทันที
**Business rule ที่เกี่ยวข้อง**: "ออเดอร์จะถูกส่งไปแสดงบน KDS ก็ต่อเมื่อการชำระเงินสำเร็จแล้วเท่านั้น"
**ประเด็นเปิด**: ไม่มี

### Epic: Dashboard ยอดขาย

#### DASH-01 — สรุปยอดขายตามช่วงเวลา
**คำอธิบาย**: สรุปยอดขายรายวัน/รายสัปดาห์/รายเดือน สำหรับเจ้าของร้านและพนักงานที่ได้รับสิทธิ์
**เหตุผลของ MoSCoW (Must)**: เป็นจุดประสงค์หลักที่ระบุไว้ตรง ๆ ของ dashboard ("ติดตามภาพรวมธุรกิจ") ไม่มี feature นี้ dashboard ไม่มีเหตุผลจะมีอยู่
**Business rule ที่เกี่ยวข้อง**: "ยอดขายที่นับในรายงานต้องมาจากออเดอร์ที่ชำระเงินสำเร็จเท่านั้น (สอดคล้องกับ QR-02)"
**ประเด็นเปิด**: ไม่มี

#### DASH-02 — ยอดขายแยกตามสินค้า/เมนูขายดี
**คำอธิบาย**: รายงานยอดขายแยกตามเมนู พร้อมจัดอันดับเมนูขายดี สำหรับวางแผนสต๊อก/โปรโมชัน
**เหตุผลของ MoSCoW (Should)**: dashboard ส่งมอบคุณค่าได้แล้วด้วยสรุปยอดขายตามช่วงเวลา (DASH-01) เพียงอย่างเดียว การแยกตามสินค้าเป็นข้อมูลเชิงลึกเสริมที่มีคุณค่าสูงแต่ไม่ blocking การเปิดใช้งาน dashboard เวอร์ชันแรก
**ประเด็นเปิด**: ไม่มี

#### DASH-03 — ตัวกรองช่วงวันที่แบบกำหนดเอง
**คำอธิบาย**: ผู้ใช้เลือกช่วงวันที่ดูรายงานได้อย่างอิสระ ไม่จำกัดแค่ตัวเลือกสำเร็จรูป
**เหตุผลของ MoSCoW (Must)**: ระบุไว้เป็น business rule ตรง ๆ ว่า "ต้องรองรับการเลือกช่วงเองแบบอิสระ (ไม่จำกัดแค่ตัวเลือกสำเร็จรูป)" และจำเป็นต่อ use case จริงที่ระบุไว้ (เช่น ดูยอดขายช่วงโปรโมชัน)
**Business rule ที่เกี่ยวข้อง**: "ตัวกรองช่วงวันที่ต้องรองรับการเลือกช่วงเองแบบอิสระ"
**ประเด็นเปิด**: ไม่มี

#### DASH-04 — Export ยอดขายเป็น CSV/Excel
**คำอธิบาย**: ปุ่ม export ข้อมูลยอดขายตามตัวกรองที่เลือกอยู่ ณ ขณะนั้น เป็นไฟล์ CSV/Excel
**เหตุผลของ MoSCoW (Should)**: มีคุณค่าชัดเจนสำหรับงานบัญชี/วิเคราะห์ต่อ แต่ dashboard ใช้งานได้ (ดูผ่านหน้าจอ) แม้ยังไม่มี export ในเวอร์ชันแรก และตัวสเปคเองยังไม่กำหนดรูปแบบ/คอลัมน์ที่ต้องมีในไฟล์ export ชัดเจน
**Business rule ที่เกี่ยวข้อง**: "ไฟล์ export ต้องมีข้อมูลตรงกับที่แสดงบนหน้าจอตามตัวกรองที่เลือกอยู่"
**ประเด็นเปิด**: รูปแบบ/คอลัมน์ที่ต้องมีในไฟล์ export ยังไม่ระบุ

#### DASH-05 — กำหนดสิทธิ์เข้าถึง dashboard (RBAC)
**คำอธิบาย**: จำกัดการเข้าถึงหน้า dashboard เฉพาะเจ้าของร้านและพนักงานที่ได้รับสิทธิ์ดูรายงานเท่านั้น
**เหตุผลของ MoSCoW (Must)**: เป็น security/business rule ที่ระบุชัดเจน — ข้อมูลยอดขายเป็นข้อมูลธุรกิจอ่อนไหว เปิดให้ทุกคนที่ login เข้าระบบได้ดูไม่ได้ ถือเป็นเงื่อนไขที่ต้องมีก่อนเปิดใช้งานจริง ไม่ใช่ nice-to-have
**Business rule ที่เกี่ยวข้อง**: "การเข้าถึงหน้า dashboard ต้องจำกัดเฉพาะผู้ใช้ที่มีบทบาท 'เจ้าของร้าน' หรือ 'พนักงานที่ได้รับสิทธิ์ดูรายงาน' เท่านั้น"
**ประเด็นเปิด**: รายละเอียดการกำหนดสิทธิ์/บทบาทผู้ใช้ (ใครกำหนดสิทธิ์พนักงาน, มีกี่ระดับสิทธิ์) ยังไม่ระบุ

#### DASH-06 — กราฟ/ชาร์ตประกอบการแสดงผล
**คำอธิบาย**: การแสดงผลข้อมูลยอดขายเป็นกราฟ/ชาร์ตประกอบตัวเลข
**เหตุผลของ MoSCoW (Could)**: **ไม่ได้อยู่ใน Scope "ทำ" ที่ยืนยันแล้วของสเปค** — หยิบมาจากหัวข้อ "ประเด็นที่ยังไม่ชัดเจน" ของสเปค dashboard ซึ่งเป็นไอเดียเปิดที่ยังไม่ได้ยืนยันว่าจะทำ ใส่ไว้ในลิสต์นี้เพื่อให้เป็น candidate ที่มองเห็นได้ ไม่ใช่ feature ที่ยืนยันแล้ว
**⚠️ ต้องยืนยันกับผู้ใช้**: feature นี้ยังไม่ผ่านการยืนยัน scope จากผู้ใช้ — ควรถามก่อนว่าจะรวมไว้ในแผนจริงหรือไม่ ถ้าไม่ต้องการให้ตัดออกจากลิสต์นี้ได้ทันที

### Epic: Audit Log & PDPA Compliance

#### AUDIT-01 — บันทึก audit log เหตุการณ์สำคัญ
**คำอธิบาย**: บันทึก log ทุกครั้งที่เกิดเหตุการณ์: สั่งออเดอร์, ชำระเงิน (สำเร็จ/ไม่สำเร็จ), แก้ไข/ลบข้อมูลสมาชิก, login เข้า dashboard, export ข้อมูล, เปลี่ยนสิทธิ์ผู้ใช้
**เหตุผลของ MoSCoW (Must)**: ระบุไว้ตรง ๆ ว่า "ไม่มีข้อยกเว้น" และเป็นรากฐานของ feature อื่นทั้งหมดในกลุ่ม audit — AUDIT-02 ถึง AUDIT-04 ทำงานไม่ได้ถ้าไม่มี logging เกิดขึ้นก่อน
**Business rule ที่เกี่ยวข้อง**: "ทุก action ในรายการต่อไปนี้ต้องถูกบันทึกเป็น audit log เสมอ ไม่มีข้อยกเว้น"
**ประเด็นเปิด**: ไม่มี (รายละเอียด async delivery mechanism เป็นประเด็นด้าน technical design ไม่ใช่ requirement)

#### AUDIT-02 — Mask ข้อมูลอ่อนไหวใน log
**คำอธิบาย**: ข้อมูลอ่อนไหว (เลขบัตรเครดิตเต็ม, รหัสผ่าน) ต้องถูก mask/ตัดทอนก่อนบันทึกลง log เสมอ
**เหตุผลของ MoSCoW (Must)**: เป็นความเสี่ยงด้านกฎหมาย/ความปลอดภัยโดยตรงหากไม่ทำ — สเปคใช้คำว่า "ห้าม...โดยเด็ดขาด"
**Business rule ที่เกี่ยวข้อง**: "ห้ามบันทึกข้อมูลอ่อนไหวแบบเต็มใน log โดยเด็ดขาด...ต้อง mask หรือตัดทอนก่อนบันทึกทุกครั้ง"
**ประเด็นเปิด**: ไม่มี

#### AUDIT-03 — Retention policy ของ log (90 วัน)
**คำอธิบาย**: Log ที่มี PII ต้องถูกลบ/anonymize อัตโนมัติเมื่อเกิน 90 วัน
**เหตุผลของ MoSCoW (Must)**: มีตัวเลขกำหนดชัดเจนในสเปคและผูกกับข้อกำหนด PDPA โดยตรง (เก็บข้อมูลส่วนบุคคลเกินความจำเป็นไม่ได้) ความเสี่ยงด้านกฎหมายถ้าไม่ทำ
**Business rule ที่เกี่ยวข้อง**: "Log ที่มี PII ต้องเก็บไว้ไม่เกิน 90 วัน แล้วลบ/เก็บถาวรแบบ anonymize"
**ประเด็นเปิด**: เทคโนโลยีจริงที่ใช้ทำ retention job เป็นประเด็น technical design รอเลือก tech stack ก่อน

#### AUDIT-04 — ป้องกันการแก้ไข/ลบ log (log integrity)
**คำอธิบาย**: Audit log ต้อง append-only หรือมีมาตรการเทียบเท่าที่ป้องกันการแก้ไข/ลบโดยไม่มีสิทธิ์ และสิทธิ์การดู log จำกัดเฉพาะ owner/system_admin
**เหตุผลของ MoSCoW (Must)**: ถ้า log แก้ไข/ลบได้โดยไม่มีการควบคุม จะทำให้ AUDIT-01 ทั้งหมดหมดความน่าเชื่อถือในฐานะหลักฐาน — เป็นเงื่อนไขที่ทำให้ feature การเก็บ log มีความหมาย
**Business rule ที่เกี่ยวข้อง**: "สิทธิ์การดู audit log จำกัดเฉพาะเจ้าของร้าน และพนักงานที่ได้รับสิทธิ์ระดับผู้ดูแลระบบ" และ "Audit log ต้อง append-only หรือมีมาตรการเทียบเท่า"
**ประเด็นเปิด**: ไม่มี (ไม่มี UI สำหรับ query log ในรอบนี้ — ดูตาราง Won't Have)

#### AUDIT-05 — Consent แบบง่ายตอนลงทะเบียนสมาชิก (PDPA)
**คำอธิบาย**: ลูกค้าต้องกดยินยอม (checkbox) พร้อมอ่าน privacy notice สั้น ๆ ก่อนสมัครสมาชิกจะสำเร็จ
**เหตุผลของ MoSCoW (Must)**: เป็นเงื่อนไข hard gate ที่ระบุตรง ๆ — ถ้าไม่กดยินยอม ระบบต้องไม่สร้างบัญชีสมาชิกได้เลย เชื่อมโยงตรงกับ QR-03 (ไม่มีสมาชิกที่ไม่ได้ consent)
**Business rule ที่เกี่ยวข้อง**: "ลูกค้าต้องกดยินยอม (consent)...ก่อนการลงทะเบียนสมาชิกจะสำเร็จ — ถ้าไม่กดยินยอม ระบบต้องไม่สร้างบัญชีสมาชิก"
**ประเด็นเปิด**: ไม่มี
