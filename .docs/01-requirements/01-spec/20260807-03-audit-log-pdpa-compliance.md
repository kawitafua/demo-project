# การเก็บ Audit Log และ PDPA Compliance

> สร้างเมื่อ 2026-08-07
> อ้างอิง: [[../01-spec/20260807-01-table-qr-ordering|20260807-01-table-qr-ordering]] (ระบบสั่งกาแฟผ่าน QR Code — แหล่งเหตุการณ์ออเดอร์/ชำระเงิน/สมาชิก)
> อ้างอิง: [[../01-spec/20260807-02-dashboard-sales|20260807-02-dashboard-sales]] (dashboard ยอดขาย — แหล่งเหตุการณ์ login/export)

## ความต้องการ (Requirement)

ระบบสั่งกาแฟผ่าน QR Code ([[../01-spec/20260807-01-table-qr-ordering|20260807-01-table-qr-ordering]]) และ dashboard ยอดขาย ([[../01-spec/20260807-02-dashboard-sales|20260807-02-dashboard-sales]]) มีการเก็บข้อมูลส่วนบุคคลของลูกค้า (สมาชิก/แต้มสะสม) และข้อมูลการชำระเงิน จึงต้องเพิ่ม requirement ด้าน Audit Log และ PDPA Compliance เพื่อให้ระบบตรวจสอบเหตุการณ์สำคัญได้ และปฏิบัติตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล (PDPA) ในระดับที่จำเป็นต่อการเริ่มเปิดใช้งานระบบ

รายละเอียดตามที่ยืนยันกับผู้ใช้:

**Audit Log — ทำเต็มตามที่แนะนำ**

- เก็บ log เหตุการณ์สำคัญ: สั่งออเดอร์, ชำระเงิน (สำเร็จ/ไม่สำเร็จ), แก้ไข/ลบข้อมูลสมาชิก, login เข้า dashboard, การ export ข้อมูล, การเปลี่ยนสิทธิ์ผู้ใช้
- แต่ละ log record ต้องมี: ผู้ทำ (user/staff id), action, เวลา (timestamp), ค่าก่อน-หลัง (สำหรับ action ที่เป็นการแก้ไข/ลบ), IP/device ถ้าจำเป็น
- ห้าม log ข้อมูลอ่อนไหวแบบเต็ม (เลขบัตรเครดิตทั้งเลข, รหัสผ่าน) — ต้อง mask/ตัดทอนข้อมูลก่อนบันทึก
- ต้องกำหนด retention period ของ log ให้ชัดเจน เพราะ log ที่มี PII ถือเป็นข้อมูลส่วนบุคคล เก็บเกินความจำเป็นไม่ได้
- ต้องป้องกันไม่ให้ log ถูกแก้ไข/ลบโดยไม่มีสิทธิ์ (log integrity)

**PDPA — ทำเท่าที่จำเป็นเท่านั้น (ตามการตัดสินใจของ user เพื่อลดความซับซ้อน)**

- เน้นเฉพาะ consent แบบง่าย: ตอนลูกค้าลงทะเบียนสมาชิก มี checkbox/ขั้นตอนขอความยินยอมเก็บ/ใช้ข้อมูล พร้อมข้อความ privacy notice สั้นๆ ว่าเก็บข้อมูลอะไร ไปใช้ทำอะไร
- ตัดออกจาก scope รอบนี้อย่างชัดเจน: ระบบ/ฟีเจอร์สำหรับ data subject rights (ขอลบ/ขอเข้าถึงข้อมูล), breach-notification workflow ในระบบ, data minimization/anonymization automation — เป็นการตัดสินใจของ user เพื่อลดความซับซ้อนของรอบนี้ ไม่ใช่การมองข้ามความสำคัญ

## Scope

- ทำ:
  - Audit log สำหรับเหตุการณ์: สั่งออเดอร์, ชำระเงิน (สำเร็จ/ไม่สำเร็จ), แก้ไข/ลบข้อมูลสมาชิก, login เข้า dashboard, การ export ข้อมูล, การเปลี่ยนสิทธิ์ผู้ใช้
  - โครงสร้าง log record: ผู้ทำ (user/staff id), action, timestamp, ค่าก่อน-หลัง (สำหรับแก้ไข/ลบ), IP/device (ถ้าจำเป็น)
  - การ mask/ป้องกันข้อมูลอ่อนไหวใน log (ไม่เก็บเลขบัตรเครดิตเต็ม, ไม่เก็บรหัสผ่าน)
  - กำหนดและบังคับใช้ retention period ของ audit log
  - มาตรการป้องกัน log ถูกแก้ไข/ลบโดยไม่มีสิทธิ์ (log integrity)
  - Consent แบบง่ายตอนลงทะเบียนสมาชิก (checkbox + privacy notice สั้นๆ)
- ไม่ทำ (ตัดออกจาก scope รอบนี้ตามการตัดสินใจของ user):
  - ฟีเจอร์ data subject rights แบบเต็มรูปแบบ (ขอลบข้อมูล/ขอเข้าถึงข้อมูลผ่านระบบ)
  - Breach-notification workflow ในระบบ
  - Data minimization / anonymization automation
  - Dashboard หรือ UI แยกสำหรับบริหารจัดการ audit log (เว้นแต่ระบุเพิ่มในอนาคต)

## User Stories / Use Cases

- ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นบันทึกว่าใครแก้ไข/ลบข้อมูลสมาชิกคนใด เมื่อไหร่ และค่าก่อน-หลังเป็นอย่างไร เพื่อตรวจสอบย้อนหลังได้เมื่อมีข้อพิพาทหรือข้อผิดพลาด
- ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นบันทึกการ login เข้า dashboard และการเปลี่ยนสิทธิ์ผู้ใช้ เพื่อตรวจสอบการเข้าถึงที่ผิดปกติ
- ในฐานะผู้ดูแลระบบ ฉันต้องการเห็นบันทึกการ export ข้อมูล เพื่อรู้ว่าข้อมูลลูกค้า/ยอดขายถูกดึงออกจากระบบโดยใครและเมื่อไหร่
- ในฐานะเจ้าของร้าน ฉันต้องมั่นใจว่า log เหตุการณ์สำคัญจะไม่ถูกแก้ไขหรือลบทิ้งโดยพนักงานที่ไม่มีสิทธิ์ เพื่อรักษาความน่าเชื่อถือของหลักฐาน
- ในฐานะลูกค้าที่ลงทะเบียนสมาชิกใหม่ ฉันต้องการเห็นข้อความสั้นๆ ว่าร้านเก็บข้อมูลอะไรของฉันไปทำอะไร และต้องกดยินยอมก่อนจึงจะสมัครสมาชิกสำเร็จ

## Business Rules / เงื่อนไข

- ทุก action ในรายการต่อไปนี้ต้องถูกบันทึกเป็น audit log เสมอ ไม่มีข้อยกเว้น: สั่งออเดอร์, ชำระเงิน (สำเร็จ/ไม่สำเร็จ), แก้ไข/ลบข้อมูลสมาชิก, login เข้า dashboard, export ข้อมูล, เปลี่ยนสิทธิ์ผู้ใช้
- Log record ต้องมีอย่างน้อย: ผู้ทำ (user/staff id), action, timestamp; สำหรับ action ที่เป็นการแก้ไข/ลบ ต้องมีค่าก่อน-หลังด้วย
- ห้ามบันทึกข้อมูลอ่อนไหวแบบเต็มใน log โดยเด็ดขาด (เลขบัตรเครดิตทั้งเลข, รหัสผ่าน) — ต้อง mask หรือตัดทอนก่อนบันทึกทุกครั้ง
- Log ที่มี PII ต้องเก็บไว้ไม่เกิน **90 วัน** แล้วลบ/เก็บถาวรแบบ anonymize ส่วน PII ทิ้งหลังพ้นกำหนด
- Audit log ต้องจัดเก็บใน**ระบบ log แยกต่างหากจากฐานข้อมูลหลัก** เพื่อแยก concern ด้าน integrity และลดผลกระทบหากฐานข้อมูลหลักถูกโจมตี
- สิทธิ์การดู audit log จำกัดเฉพาะ **เจ้าของร้าน และพนักงานที่ได้รับสิทธิ์ระดับผู้ดูแลระบบ** เท่านั้น (เป็นสิทธิ์คนละชุดกับสิทธิ์ดู dashboard ยอดขายตาม [[../01-spec/20260807-02-dashboard-sales|20260807-02-dashboard-sales]])
- Audit log ต้อง append-only หรือมีมาตรการเทียบเท่าที่ป้องกันการแก้ไข/ลบโดยไม่มีสิทธิ์ (log integrity)
- ลูกค้าต้องกดยินยอม (consent) ผ่าน checkbox พร้อมอ่าน privacy notice สั้นๆ ก่อนการลงทะเบียนสมาชิกจะสำเร็จ — ถ้าไม่กดยินยอม ระบบต้องไม่สร้างบัญชีสมาชิก
- Privacy notice ต้องระบุอย่างน้อย: เก็บข้อมูลอะไร (เช่น ชื่อ, เบอร์โทร, ประวัติการสั่งซื้อ, แต้มสะสม) และนำไปใช้ทำอะไร (เช่น สะสมแต้ม, แจ้งโปรโมชัน)

## ประเด็นที่ยังไม่ชัดเจน (รอตัดสินใจในรอบถัดไป)

ประเด็น retention period, สิทธิ์การดู audit log, และรูปแบบการจัดเก็บ ได้รับการยืนยันกับ user แล้ว (ดู Business Rules ด้านบน) ประเด็นที่ยังเหลือค้าง:

- ขอบเขต PDPA ที่ตัดออกไปในรอบนี้ (data subject rights, breach notification, anonymization automation) ให้เก็บไว้เป็นประเด็นรอทำในอนาคต หากภาระทางกฎหมายหรือธุรกิจเปลี่ยนไป
- รายละเอียดทางเทคนิคของ "ระบบ log แยกต่างหาก" (เช่น จะใช้ log service ใด, self-hosted หรือ cloud) ยังไม่ระบุ — รอวิเคราะห์ในเอกสารออกแบบ ([[../../02-design/02-technical/index|02-technical]])
