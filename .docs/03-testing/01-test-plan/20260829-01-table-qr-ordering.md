## ขอบเขตการทดสอบ (Scope)

- ทดสอบ:
  - การสแกน QR Code เปิดหน้าเมนู และการระบุหมายเลขโต๊ะอัตโนมัติ (`QR-01`)
  - ตะกร้าสินค้าและการชำระเงินออนไลน์ในระบบ ผ่านช่องทางที่รองรับครบทั้ง 3 ช่องทาง (พร้อมเพย์, บัตรเครดิต/เดบิต, e-wallet) รวมถึงเงื่อนไข gate ระหว่างการชำระเงินกับการส่งออเดอร์ไป KDS และการคำนวณแต้มสะสม (`QR-02`)
  - เงื่อนไขการลองชำระเงินใหม่เมื่อชำระเงินไม่สำเร็จ สูงสุด 3 ครั้งต่อออเดอร์ (`QR-02`)
  - การคำนวณแต้มสะสมจากยอดชำระที่สำเร็จ ในอัตราทุก 10 บาท = 1 แต้ม สำหรับลูกค้าที่เป็นสมาชิก (`QR-03`)
  - เงื่อนไข consent ที่ gate การสมัครสมาชิกระหว่างขั้นตอนสั่งซื้อ (`AUDIT-05` ที่เชื่อมกับ flow นี้)
  - การแสดงผลออเดอร์บนจอ KDS แบบเรียลไทม์ เฉพาะออเดอร์ที่ชำระเงินสำเร็จ (`QR-04`)
- ไม่ทดสอบ (out of scope รอบนี้):
  - สถานะออเดอร์บน KDS หลังบาริสต้าเริ่มทำ (mark "กำลังทำ"/"เสร็จแล้ว") เนื่องจากยังไม่มี requirement รองรับ (ดู [[../../02-design/01-prototypes/20260829-01-user-journeys|user journeys]] Journey 2)
  - กลไก real-time เบื้องหลัง (WebSocket/polling) เป็นประเด็นด้าน technical design ไม่ใช่ acceptance testing
  - การใช้/แลกแต้มสะสม (redemption) — สเปคระบุเฉพาะเงื่อนไขการ**สะสม**แต้มเท่านั้น ยังไม่มี business rule เรื่องการแลกแต้ม
  - รายละเอียด UX ปลีกย่อยของแต่ละช่องทางชำระเงิน (เช่น หน้าจอเฉพาะของผู้ให้บริการบัตร/wallet แต่ละราย) เป็นประเด็นด้าน technical/prototype design ไม่ใช่ acceptance testing ระดับนี้

> หมายเหตุ: เดิมทั้ง 3 หัวข้อ "ช่องทางชำระเงิน", "อัตราการสะสมแต้ม" และ "การจัดการชำระเงินไม่สำเร็จ" เคยอยู่ใน out-of-scope เพราะสเปครอการยืนยันจาก user — **user ได้ยืนยันคำตอบแล้วเมื่อ 2026-08-29** (ดู Business Rules ในสเปคที่อัปเดตแล้ว) จึงย้ายกลับมาอยู่ใน scope การทดสอบรอบนี้ โปรดสังเกตว่าเงื่อนไข "ลองชำระใหม่ได้สูงสุด 3 ครั้ง" เป็นค่าที่ AI แนะนำแทน user (user ตอบว่า "แนะนำให้เลย") ไม่ใช่ตัวเลขที่ user กำหนดเองโดยตรง

## Test Environment / Test Data

- อุปกรณ์: มือถือ (จำลองการสแกน QR / เข้าหน้าเว็บสั่งเมนูโดยตรงด้วย URL ที่ผูกหมายเลขโต๊ะ), tablet/จอในร้านสำหรับ KDS
- ข้อมูลทดสอบ: QR Code/URL ที่ผูกกับอย่างน้อย 2 หมายเลขโต๊ะ (เช่น โต๊ะ #4, โต๊ะ #7) เพื่อยืนยันว่าไม่มีการสลับโต๊ะ
- บัญชีทดสอบ: ลูกค้าที่เป็นสมาชิกอยู่แล้ว 1 บัญชี, ลูกค้าใหม่ที่ยังไม่สมัครสมาชิก 1 กรณี
- เมนูทดสอบอย่างน้อย 2-3 รายการที่มีราคาต่างกัน เพื่อคำนวณยอดรวมตะกร้า
- สภาพแวดล้อมการชำระเงิน: ใช้ sandbox/mock payment gateway ที่จำลองผลลัพธ์ได้ทั้งกรณีสำเร็จและไม่สำเร็จ ครบทั้ง 3 ช่องทางที่ต้องรองรับ (พร้อมเพย์, บัตรเครดิต/เดบิต, e-wallet) และสามารถบังคับให้ล้มเหลวซ้ำได้ต่อเนื่องเพื่อทดสอบเงื่อนไข retry (3 ครั้ง)
- ยอดชำระตัวอย่างสำหรับทดสอบอัตราแต้มสะสม (10 บาท = 1 แต้ม): ฿185 (คาดว่าได้ 18 แต้ม, ปัดเศษลง), ฿200 (คาดว่าได้ 20 แต้ม พอดี ไม่มีเศษ)

| TC-17 | ลองชำระเงินใหม่ภายใน 3 ครั้งจนสำเร็จ ต้องดำเนินการต่อได้ปกติ | มีสินค้าในตะกร้าแล้ว | 1. ชำระเงินครั้งที่ 1 ให้ไม่สำเร็จ 2. กดลองชำระเงินใหม่ (ครั้งที่ 2) ให้ไม่สำเร็จอีก 3. กดลองชำระเงินใหม่ (ครั้งที่ 3) ให้สำเร็จ | ระบบยังคงเป็นออเดอร์เดิม (ไม่สร้างออเดอร์ใหม่) อนุญาตให้ลองชำระใหม่ได้ทั้ง 2 ครั้งก่อนหน้า และเมื่อครั้งที่ 3 สำเร็จ ออเดอร์ต้องส่งไป KDS ตามปกติ | AC5, AC6 |
| TC-18 | ชำระเงินไม่สำเร็จครบ 3 ครั้งติดต่อกัน → ต้องไม่ให้ลองซ้ำอีก และต้องเริ่มออเดอร์ใหม่ | มีสินค้าในตะกร้าแล้ว | 1. ชำระเงินครั้งที่ 1, 2, 3 ให้ไม่สำเร็จทั้งหมด 2. หลังครั้งที่ 3 สังเกตหน้าจอ 3. ลองมองหาปุ่ม/ทางเลือก "ลองชำระเงินใหม่" กับออเดอร์เดิม | หลังล้มเหลวครบ 3 ครั้ง ระบบต้อง**ไม่**เสนอทางเลือกลองชำระซ้ำกับออเดอร์เดิมอีก และต้องแจ้ง/บังคับให้ลูกค้าเริ่มออเดอร์ใหม่ (กลับไปหน้าเมนู/ตะกร้าเพื่อสั่งใหม่) | AC6 |
