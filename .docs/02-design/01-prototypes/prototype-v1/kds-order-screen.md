# จอ KDS (Kitchen Display System — บาริสต้า)

> สร้างเมื่อ 2026-08-29
> อ้างอิง Design System: [[../20260829-02-design-system|20260829-02-design-system]] (หัวข้อ 2.1-2.6 Design Tokens, 3.1 Components ร่วม, 3.3 จอ KDS, 4.3 ความเร็วในการอ่านสำหรับบาริสต้า)
> อ้างอิง Requirement: [[../../../01-requirements/01-spec/20260807-01-table-qr-ordering|20260807-01-table-qr-ordering]]
> อ้างอิง Feature: `QR-04` (ดู [[../../../01-requirements/02-plan/20260829-01-feature-list|20260829-01-feature-list]]) / Journey step: [[../20260829-01-user-journeys#Journey 2: บาริสต้ารับออเดอร์ผ่าน KDS|Journey 2: บาริสต้ารับออเดอร์ผ่าน KDS]]

หน้าจอนี้แสดงออเดอร์ที่ **ชำระเงินสำเร็จแล้วเท่านั้น** ให้บาริสต้าเห็นแบบเรียลไทม์ (`QR-04`) ออกแบบสำหรับจอในร้าน (tablet/in-store display, breakpoint `tablet` ตาม Design System หัวข้อ 2.6) เน้นความเร็วในการอ่านจากระยะไกล 1-2 เมตรระหว่างทำงาน (Design System หัวข้อ 4.3)

รอบนี้ครอบคลุม 3 state: **(1) Ticket Grid ปกติ → (2) New Order Highlight (ออเดอร์ใหม่เข้าแบบเรียลไทม์) → (3) Empty State (ยังไม่มีออเดอร์)**

> ⚠️ **ข้อจำกัดสำคัญที่ prototype นี้ตั้งใจสะท้อนไว้**: ตาม [[../20260829-01-user-journeys#Journey 2: บาริสต้ารับออเดอร์ผ่าน KDS|Journey 2]] ขั้นตอนที่ 3 ("บาริสต้าเตรียมเครื่องดื่ม") **ยังไม่มี business rule/requirement รองรับสถานะออเดอร์อย่างเป็นทางการ** (เช่น ปุ่ม mark "กำลังทำ" / "เสร็จแล้ว" หรือการนำออเดอร์ออกจากจอเมื่อเสร็จ) สเปคต้นทาง [[../../../01-requirements/01-spec/20260807-01-table-qr-ordering|table-qr-ordering]] ระบุเพียงว่าออเดอร์ "แสดงผลบนจอ...แบบเรียลไทม์" เท่านั้น ไม่ได้พูดถึง flow หลังจากนั้น ดังนั้น wireframe ด้านล่าง**จะไม่วาดปุ่ม/สถานะเหล่านี้เป็นเรื่องยืนยันแล้ว** — แสดงไว้เพียงกรอบ "ประเด็นเปิด" ต่อท้าย state 1 เพื่อสื่อสารช่องว่างนี้กลับไปยังทีม requirement

## Wireframe — State 2: New Order Highlight (ออเดอร์ใหม่เข้าแบบเรียลไทม์)

```
+--------------------------------------------------------------------------------+
| [Wordmark: my-coffee-store]                       จอครัว (KDS)      12:42 น.    |
+--------------------------------------------------------------------------------+
|                                                                                  |
|  +------------------+   +------------------+   +------------------+           |
|  |  โต๊ะ #4          |   |  โต๊ะ #7          |   |  โต๊ะ #2          |           |
|  |  สั่งเมื่อ 12:35   |   |  สั่งเมื่อ 12:38   |   |  สั่งเมื่อ 12:40   |           |
|  |  ------------------|   |------------------|   |------------------|           |
|  |  ลาเต้ร้อน   x2     |   |  อเมริกาโน่เย็น x1 |   |  คาปูชิโน่   x1    |           |
|  |  อเมริกาโน่ร้อน x1  |   |  มอคค่าเย็น   x1   |   |  ชาเขียวลาเต้ x2   |           |
|  +------------------+   +------------------+   +------------------+           |
|                                                                                  |
|  +------------------+   +==================+                                   |
|  |  โต๊ะ #9          |   ‖  โต๊ะ #5          ‖  <-- New Order Highlight            |
|  |  สั่งเมื่อ 12:41   |   ‖  สั่งเมื่อ 12:42   ‖      (ขอบหนา 2px                     |
|  |  ------------------|   ‖------------------‖       --color-brand-secondary--,   |
|  |  ลาเต้เย็น   x3     |   ‖  ลาเต้ร้อน   x1     ‖      ไม่มี animation กระพริบ           |
|  |                    |   ‖  ชาไทย        x1     ‖      ตาม UX 4.3 — จางกลับเป็น     |
|  +------------------+   +==================+       ขอบปกติหลังบาริสต้าเปิดดู)       |
|                                                                                  |
+--------------------------------------------------------------------------------+
```

- การ์ด "โต๊ะ #5" เพิ่งเข้ามาแบบเรียลไทม์ (ออเดอร์ชำระเงินสำเร็จจาก [[../20260829-01-user-journeys#Journey 1: ลูกค้าสั่งกาแฟผ่าน QR Code|Journey 1]] ขั้นตอนที่ 7) — ใช้ **New Order Highlight** ตาม Design System หัวข้อ 3.3: ขอบหนา `--color-brand-secondary` 2px แบบ static ไม่กระพริบ/สั่น เพื่อไม่รบกวนสมาธิระหว่างชงกาแฟ (หัวข้อ 4.3)
- ตำแหน่งการ์ดใหม่ยังคงเรียงตามลำดับเวลาเข้า (เก่าสุดซ้ายบน) ไม่กระโดดมาอยู่ตำแหน่งพิเศษ เพื่อความสม่ำเสมอของ layout

## Wireframe — State 3: Empty State (ยังไม่มีออเดอร์)

```
+--------------------------------------------------------------------------------+
| [Wordmark: my-coffee-store]                       จอครัว (KDS)      09:02 น.    |
+--------------------------------------------------------------------------------+
|                                                                                  |
|                                                                                  |
|                        [ไอคอน line 24px: ถ้วยกาแฟ]                               |
|                        --color-text-secondary--                                |
|                                                                                  |
|                     ยังไม่มีออเดอร์เข้ามาในขณะนี้                                     |
|                     --text-h2--                                                 |
|                                                                                  |
|                 ออเดอร์ที่ลูกค้าชำระเงินสำเร็จจะแสดงที่นี่ทันที                          |
|                 --text-caption--, --color-text-secondary--                     |
|                                                                                  |
+--------------------------------------------------------------------------------+
```

- ใช้ **Empty State** component ตาม Design System หัวข้อ 3.1 (ไอคอน line 24px + ข้อความอธิบายสั้น ไม่มี CTA เพราะไม่มี action ให้กดในบริบทนี้)
- ไม่ใช้สีเน้น/accent ใดๆ เพื่อไม่ดึงความสนใจเกินจำเป็นในสถานะที่ไม่มีอะไรต้องทำ

## ประเด็นที่ยังไม่ยืนยัน (สืบทอดจาก requirement ต้นทาง — ยังไม่ใช่การตัดสินใจใหม่ของ prototype นี้)

- **ไม่มี requirement รองรับสถานะออเดอร์หลังบาริสต้าเริ่มทำ** (เช่น mark "กำลังทำ" / "เสร็จแล้ว" หรือวิธีเอาการ์ดออกจากจอ) — ตามที่ [[../20260829-01-user-journeys#Journey 2: บาริสต้ารับออเดอร์ผ่าน KDS|Journey 2]] ระบุไว้ชัดว่าเป็นประเด็นเปิด wireframe ทั้ง 3 state นี้จึงไม่มี UI ส่วนนี้ ควรสอบถามผู้ใช้/ทีม requirement เพื่อเพิ่ม business rule รองรับก่อนพัฒนาจริง
- กลไก real-time ที่ใช้ส่งข้อมูลไปยังจอ KDS (WebSocket/polling ฯลฯ) เป็นประเด็น technical design ไม่ใช่ requirement — ไม่ได้ระบุใน wireframe นี้
- จำนวนคอลัมน์สูงสุดของ Ticket Grid ต่อขนาดจอจริง (เช่น รองรับกี่ออเดอร์พร้อมกันก่อนต้อง scroll แนวตั้ง) ยังไม่ระบุในสเปค — wireframe นี้แสดงตัวอย่าง 3 คอลัมน์เพื่อสื่อโครง ไม่ใช่ตัวเลขสุดท้าย
